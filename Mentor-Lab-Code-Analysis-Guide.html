CHAPTER 01

Project at a Glance

Mentor Lab is a full-stack study platform for BCA, BBA and Biotechnology students. It combines course material, previous-year papers, mock tests, performance analytics and certificates in one React application backed by an Express API and MongoDB.

1.1 What the platform does

The application is not a single-purpose website. It has several independent learning modules that share one authentication system and one database:

Naming inconsistency

The public brand is Mentor Lab, but the frontend package is named drona-gyan and some UI text still says “Drona Gyan” or “Monitor Lab”. The backend package is named monitor-lab-backend. This is a presentation inconsistency, not a runtime failure, but it should be standardised before a formal demo.

1.4 The central design idea

Every student action is tied to the same identity: the MongoDB User document referenced in the JWT. That one identity links purchases, test results, read notes and certificates:

One identity, many modules
JWT{ id } signed for 7 days
→
protectloads User and removes password
→
Feature routeuses req.user._id
→
MongoDBPurchase, Result, readNotes, Certificate

This is why the project can be explained simply in a viva: authentication establishes req.user; every protected feature then uses that user id to read or write its own collection.

1.5 Strengths worth highlighting

  • Complete feature loop: content → practice → scoring → progress → certificate.
  • Separation of concerns: routes, controllers, models, utilities and middleware are separated on the backend.
  • Real file storage: PDFs are stored in MongoDB GridFS, not just as paths in the database.
  • Payment fallback: Razorpay when configured, manual UPI confirmation otherwise.
  • Security awareness in auth: bcrypt hashing, hashed OTPs, OTP expiry, resend cooldown, attempt limits and one-time reset tokens.
  • Resilient note reading: existing PDFs can be lazily converted to text on first view.

1.6 Weaknesses to acknowledge honestly

Viva framing

Do not claim the project is production-perfect. Say: “The core learning loop is complete and functional; the next engineering pass would harden authorisation, verify manual payments, centralise API URLs, and add automated tests.” That answer is stronger than pretending there are no gaps.

Architecture and Request Lifecycle

A single request crosses several boundaries: browser component → Axios → Vite proxy or Express static server → middleware → route → controller/route handler → Mongoose → MongoDB → JSON → React state.

3.1 High-level architecture

↔
Express 5CORS, JSON, routes, static files, SPA fallback
↔

↔
MongoDBAtlas/local database

External services sit beside this chain: Groq for language-model responses, Google Translate TTS for Hindi audio, Razorpay for card/UPI checkout, Wandbox for code compilation, and SMTP for password-reset email.

3.2 Backend middleware order

backend/src/index.js is short but its order matters:

  1. cors() allows the dev frontend origin to call the API.
  2. express.json() parses JSON bodies for login, tests, AI and payment routes.
  3. Eight API routers are mounted under /api/....
  4. /uploads serves disk files and forces inline display for PDFs.
  5. A second /uploads handler returns JSON 404 for missing files.
  6. express.static(frontendDist) serves the built React assets.
  7. app.get("/{*path}") returns index.html for client-side routes.
  8. The database connects, then the server listens on PORT || 5000.
Startup ordering detail

The server calls connectDB() and app.listen() without awaiting the database. If MongoDB is unavailable, the connection function exits the process after its 5-second timeout, but the listener has already been created. In practice the process dies, yet a cleaner design is await connectDB(); app.listen(...).

Server Bootstrap and MongoDB

Two small files define the entire runtime foundation: src/index.js creates the Express application and mounts every feature, while src/db.js owns the MongoDB connection and failure policy.

4.1 The Express entry point

backend/src/index.js imports express, dotenv, cors, path, the database connector and all eight route modules. It computes three directory anchors:

const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);
const rootDir = path.resolve(__dirname, "..");

__dirname is backend/src; rootDir is backend. Those anchors are used for backend/uploads and frontend/dist. Because the package declares "type": "module", ES module syntax is used throughout and __dirname must be reconstructed manually.

Middleware and routes

const app = express();
app.use(cors());
app.use(express.json());

app.use("/api/auth", authroutes);
app.use("/api/admin", adminRoutes);
app.use("/api/mocktest", mockTestRoutes);
app.use("/api/notes", notesRoutes);
app.use("/api/pyq", pyqRoutes);
app.use("/api/ai", aiRoutes);
app.use("/api/payment", paymentRoutes);
app.use("/api/certificate", certificateRoutes);

There is no global error handler, request logger, rate limiter, helmet security header layer, or body-size limit beyond Express defaults. JSON parsing is global, so every JSON route depends on it. The CORS configuration is wide open (cors() with no origin allowlist), which is convenient during development but should be restricted in production.

Static files and SPA fallback

const uploadsDir = path.join(rootDir, "uploads");
app.use("/uploads", express.static(uploadsDir, {
  setHeaders: (res, p) => {
    if (p.endsWith(".pdf")) res.set("Content-Disposition", "inline");
  }
}));
app.use("/uploads", (req, res) => {
  res.status(404).json({ message: "File not found" });
});

const frontendDist = path.resolve(rootDir, "..", "frontend", "dist");
app.use(express.static(frontendDist));
app.get("/{*path}", (req, res) => {
  res.sendFile(path.join(frontendDist, "index.html"));
});

The first /uploads handler serves real files. The second is a deliberate 404 fallback so a missing upload returns JSON rather than falling through to the React application. The SPA catch-all must come after API routes; otherwise API paths would return HTML.

Express 5 syntax

app.get("/{*path}", ...) is Express 5 wildcard syntax. In Express 4 the equivalent would be app.get("*", ...). This is one reason the project requires Express 5.

Startup sequence

const port = process.env.PORT || 5000;
connectDB();
app.listen(port, () => {
  console.log(`Server running on port ${port}`);
});

The database connection is started but not awaited. This keeps startup code compact but has a lifecycle weakness: the HTTP listener can be created before the database is ready. Since connectDB() calls process.exit(1) on failure, the process still stops, but a safer pattern is:

await connectDB();
app.listen(port, () => console.log(`Server running on port ${port}`));

5.3 Registration: validation before creation

register reads firstName, middleName, lastName, email, password and phone. It validates names, phone shape and email domain before touching the database.

Name validation

const nameOnlyRegex = /^[a-zA-Z]+(?:\s[a-zA-Z]+)*$/;
if (firstName !== undefined && (!firstName.trim() || !nameOnlyRegex.test(firstName.trim()))) {
  return res.status(400).json({ message: "First name must contain only letters" });
}

Letters and internal single spaces are allowed. Numbers, punctuation and leading/trailing whitespace after trim fail.

Phone validation

The frontend sends a combined string such as +919876543210. The backend splits it with /^(\+\d+)(\d+)$/, looks up the expected national number length in a large country-code table, and checks that the remainder is all digits and has the expected length.

const match = phone.match(/^(\+\d+)(\d+)$/);
const code = match ? match[1] : "";
const number = match ? match[2] : phone;
const expectedLen = countryPhoneLength(code);
if (!/^[0-9]+$/.test(number) || (expectedLen && number.length !== expectedLen)) {
  return res.status(400).json({ message: "Please enter a valid phone number..." });
}

For countries absent from the table, expectedLen is undefined, so only the digits check applies. This is intentionally permissive but not a full libphonenumber implementation.

Email domain allowlist

The backend accepts only a list of well-known providers (gmail.com, yahoo.com, outlook.com, proton.me, and others). A college or company domain is rejected even if the address is valid. This is a product decision, not a standard email validation rule.

5.4 Login and password comparison

User.password is declared with select: false, so ordinary queries omit it. Login explicitly asks for it:

Using the same message for unknown email and wrong password avoids account enumeration. On success the response contains _id, name, email, isAdmin and a JWT.

Token construction

backend/utils/generateToken.js:

jwt.sign({ id }, process.env.JWT_SECRET, { expiresIn: "7d" });

The payload is deliberately tiny. It contains no role and no email, so role changes take effect on the next request because protect reloads the user document. A seven-day expiry is convenient for students but there is no refresh token, logout revocation list, or token versioning. A stolen token remains usable until expiry unless the secret is rotated.

5.5 The protect middleware

backend/middleware/authMiddleware.js:

if (req.headers.authorization && req.headers.authorization.startsWith("Bearer")) {
  try {
    token = req.headers.authorization.split(" ")[1];
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.user = await User.findById(decoded.id).select("-password");
    next();
  } catch (error) {
    res.status(401).json({ message: "Not authorized, token failed" });
  }
}
if (!token) {
  res.status(401).json({ message: "Not authorized, no token" });
}

Important details:

  • The header must begin exactly with Bearer; a malformed header falls into the no-token branch.
  • jwt.verify checks both signature and expiry.
  • The user is reloaded from MongoDB on every protected request, so isAdmin and profile data are current.
  • If the token is valid but the user was deleted, req.user is null and next() still runs. Downstream code that assumes req.user._id will throw a 500 rather than returning 401.
  • There is no explicit token scheme validation beyond split(" ")[1].
Suggested hardening

After findById, check if (!req.user) return res.status(401).... Also return immediately after the 401 in the catch block to make the control flow unambiguous.

5.6 Password reset: the full OTP state machine

This is the most detailed logic in the project. Constants:

ConstantValueMeaning
OTP_TTL_MS10 × 60 × 1000OTP valid for 10 minutes.
OTP_RESEND_COOLDOWN_MS60 × 100060-second wait before a new code.
OTP_MAX_ATTEMPTS5Five wrong tries, then the OTP is invalidated.

Step 1 — request a code

const email = String(req.body.email || "").trim().toLowerCase();
const genericMessage = "If an account exists for that email, a verification code has been sent.";
const user = await User.findOne({ email }).select(
  "+resetOtpHash +resetOtpExpires +resetOtpRequestedAt +resetOtpAttempts"
);
if (!user) return res.status(200).json({ message: genericMessage });

The generic response prevents attackers from discovering registered emails. The cooldown is enforced next; if the last request was under 60 seconds ago, the API returns 429 with a retryAfter value.

const otp = String(crypto.randomInt(100000, 1000000));
user.resetOtpHash = await bcrypt.hash(otp, 10);
user.resetOtpExpires = new Date(now + OTP_TTL_MS);
user.resetOtpRequestedAt = new Date(now);
user.resetOtpAttempts = 0;
await user.save();

The six-digit code is generated with a cryptographic random integer and only its bcrypt hash is stored. The plaintext code exists long enough to be emailed.

Step 2 — verify the code

The controller validates a six-digit format, checks expiry, checks the attempt cap, and compares with bcrypt.compare. A wrong code increments resetOtpAttempts. An expired code or exhausted attempt count clears the OTP state.

const resetJti = crypto.randomBytes(24).toString("hex");
user.resetOtpHash = null;
user.resetOtpExpires = null;
user.resetOtpRequestedAt = null;
user.resetOtpAttempts = 0;
user.resetTokenHash = hashToken(resetJti);
await user.save();

const resetToken = jwt.sign(
  { id: user._id, purpose: "password-reset", jti: resetJti },
  process.env.JWT_SECRET,
  { expiresIn: "10m" }
);

This is a two-layer one-time token design:

  • The JWT is signed, expires in ten minutes, and contains a random jti.
  • Only the SHA-256 hash of that jti is stored in the user document.
  • Resetting consumes the stored hash, so replaying the same token fails.
  • purpose: "password-reset" prevents a normal login token from being accepted as a reset token.

Step 3 — set a new password

if (!isStrongPassword(password)) return res.status(400).json({ ... });
decoded = jwt.verify(resetToken, process.env.JWT_SECRET);
if (decoded.purpose !== "password-reset" || !decoded.id || !decoded.jti) ...
if (!user.resetTokenHash || user.resetTokenHash !== hashToken(decoded.jti)) ...
user.password = await bcrypt.hash(password, salt);
user.resetTokenHash = null;

The strong-password rule is: at least 8 characters, at least one letter, at least one number, and at least one non-alphanumeric character.

5.7 Email delivery and the development OTP

utils/mailer.js checks whether SMTP_HOST, SMTP_USER and SMTP_PASS exist. If not, it returns { delivered: false } without throwing. The controller then logs a warning containing the OTP and may include devOtp in the JSON response when NODE_ENV !== "production".

OTP leakage risk

When SMTP is unavailable, the server writes the plaintext OTP to the console. That is acceptable for a local demo only if logs are private. More importantly, if NODE_ENV is not set to production on a deployed server, devOtp is returned to the client. Always set NODE_ENV=production and configure SMTP before deployment.

5.8 Authentication: what to say in the viva

“Passwords are hashed with bcrypt and never returned. Login issues a signed JWT containing the user id, valid for seven days. Protected routes verify the signature, reload the user and attach it to the request. Password reset uses a six-digit OTP stored only as a bcrypt hash, with a ten-minute expiry, a 60-second resend cooldown, a five-attempt limit, and a one-time reset JWT whose random id is hashed in the database.”

8.4 extractPdfText

async function extractPdfText(buffer) {
  try {
    const parser = new PDFParse(new Uint8Array(buffer));
    await parser.load();
    const result = await parser.getText();
    const text = (result.pages || []).map((p) => p.text || "").join("\n");
    return text.trim() || "";
  } catch (error) {
    console.error("PDF text extraction failed:", error.message);
    return "";
  }
}

Extraction failure is non-fatal: the PDF is still stored, but hasContent is false and the viewer says no online content is available. This is a sensible resilience choice. The parser is pdf-parse v2, imported as a named export in this file.

8.5 GridFS buckets

const getBucket = () =>
  new mongoose.mongo.GridFSBucket(mongoose.connection.db, { bucketName: "pdfs" });

Each call creates a bucket handle against the active connection. GridFS splits files into chunks, so a PDF can exceed MongoDB’s 16 MB document limit. The file metadata keeps the original name and title/course/subject.

Two buckets, one pattern

Notes use pdfs; PYQs use pyqs. Keeping them separate makes deletion and inspection simpler and avoids filename collisions between the two content types.

8.7 Lazy extraction on first view

Older notes may have a fileId but no content. When GET /api/notes/:id sees that condition, it downloads the PDF from GridFS, extracts the text, saves it, and returns the updated note:

  if (text) {
    note.content = text;
    note.hasContent = true;
    await note.save();
  }
}

This is a lazy migration strategy. The first request is slower; subsequent requests read the stored text. It also means a read-only GET performs a write, which is acceptable here but should be noted in the design discussion.

10.4 parseQuestions: the core algorithm

The parser expects plain text in a predictable exam format:

1. What is the capital of India?
(A) Mumbai
(B) New Delhi
(C) Kolkata
(D) Chennai
Answer: B

It first normalises lines:

const lines = text.split('\n').map(l => l.trim()).filter(l => l.length > 0);
let currentQuestion = null;

Question detection

const qMatch = line.match(/^(?:Q)?(\d+)[\.\)]\s+(.*)/i);
if (qMatch) {
  if (currentQuestion) questions.push(currentQuestion);
  currentQuestion = { question: qMatch[2], options: [], correctAnswer: "" };
  return;
}

Accepted starts include 1., 1), Q1. and q1). When a new question begins, the previous one is pushed.

Multiple options on one line

const regex = /\(?([A-Da-d])\)?[\.\)]\s+/g;

The parser finds all option markers in a line. If there is more than one, it slices the text between markers. This supports both:

(A) Mumbai  (B) New Delhi  (C) Kolkata  (D) Chennai

and each option on its own line. It caps options at four.

Answer detection

const aMatch = line.match(/^(?:Ans|Answer|Correct)[:\s]+\(?([A-Da-d])\)?/i);
const idx = "ABCD".indexOf(ansVal);
if (idx >= 0 && currentQuestion.options[idx]) {
  currentQuestion.correctAnswer = currentQuestion.options[idx];
} else {
  currentQuestion.correctAnswer = ansVal;
}

The stored correct answer is normally the option text, not the letter. That matters for scoring, which compares selected option text with q.correctAnswer. If the answer appears before options are parsed, the letter is stored instead and scoring will not match.

Continuation lines

if (currentQuestion) {
  if (currentQuestion.options.length === 0) {
    currentQuestion.question += " " + line;
  } else {
    const lastIdx = currentQuestion.options.length - 1;
    currentQuestion.options[lastIdx] += " " + line;
  }
}

Wrapped question or option text is appended to the current field. This is a heuristic: a stray heading after the options can be appended to the last option.

const hasAccess = async (userId, test) => {

11.6 Razorpay verification

const expected = crypto
  .createHmac("sha256", process.env.RAZORPAY_KEY_SECRET)
  .update(`${orderId}|${paymentId}`)
  .digest("hex");
if (expected !== signature) {
  return res.status(400).json({ message: "Payment verification failed" });
}

This is the standard Razorpay signature check. It proves the order/payment pair was signed by the server’s secret. On success, a purchase row is upserted with status: "paid".

Amount is not re-verified

The route trusts the test price in the database and does not fetch the Razorpay payment to compare its amount or status. Signature verification is strong, but a production implementation should also query Razorpay for the payment and confirm the captured amount, currency and order id.

11.8 Submission and scoring

The client sends an object keyed by question index:

{ "0": 2, "1": 0, "3": 1 }

The server loops over every test question:

test.questions.forEach((q, idx) => {
  if (answers[idx] !== undefined) {
    computedAttempted++;
    const selectedAnswer = q.options[answers[idx]];
    const isCorrect = selectedAnswer === q.correctAnswer;
    if (isCorrect) computedCorrect++;
    else computedWrong++;
    detailedAnswers.push({ ... });
  } else {
    detailedAnswers.push({
      questionIndex: idx, selectedOption: -1, isCorrect: false,
      correctAnswer: q.correctAnswer, selectedAnswer: null,
    });
  }
});
const computedScore = (computedCorrect * 4) - (computedWrong * 1);
score = (correct × 4) − (wrong × 1)   |   maxScore = totalQuestions × 4

Unattempted questions do not reduce the score. A test with 10 questions has a maximum of 40. If a student answers 5 correctly and 3 incorrectly, the score is 20 − 3 = 17; two unattempted questions contribute nothing.

The Result document stores:

  • full answers array with question index, selected option, correctness, correct answer and selected answer;
  • score and maxScore;
  • attempted, correct and wrong;
  • userId, testId, title and timestamps.

11.9 Server-side scoring is a strength

The browser never receives the correct answers while taking the test, and the client cannot submit a score. The server calculates everything from the stored question set. This is the right trust boundary and should be highlighted in the viva.

  • Only the existence of a result matters, not the score. A student can fail a test and still count it as attempted.

  email: data.email, _id: data._id, isAdmin: data.isAdmin || false,

Notice that isAdmin is stored inside the user object, not as the separate isAdmin key used by the navbar and AdminRoute. A normal signup therefore does not make the admin UI appear.

15.2 Email-domain allow-list

Both signup and login contain a long famousDomains array: Gmail, Yahoo variants, Outlook, Hotmail, Live, Rediffmail, Proton, iCloud, AOL, Zoho, Yandex, Fastmail, GMX, Tutanota, Rocketmail, Inbox and Mail.ru.

const domain = email.split("@")[1].toLowerCase();
if (!famousDomains.includes(domain)) {
  alert("Please use a well-known email provider (Gmail, Yahoo, Outlook, etc.)");
}

This blocks legitimate college and company addresses. It also duplicates the backend’s disposable-domain check. Keep format validation on the client and make the server the single authority for allowed domains.

15.3 Login flow

The login form validates email format, the same provider allow-list, and a password of at least six characters. It posts to /api/auth/login, then:

localStorage.clear();
localStorage.setItem("token", response.data.token);
window.location.href = "/";

Normal login stores only the token. It does not store user or isAdmin, and it clears any previous values. The navbar still treats the session as logged in because it checks only the token. Profile data is refetched from the API.

Client-side password minimum

Login accepts six characters while signup requires eight plus complexity. Existing accounts may have shorter passwords, but the mismatch is confusing. The backend remains responsible for verifying the password; client checks are only usability hints. The “Remember me” checkbox is not wired to any behaviour.

15.6 Admin login

AdminLogin.jsx uses the same POST /api/auth/login endpoint as the student login. After a successful response it checks response.data.isAdmin:

  localStorage.setItem("isAdmin", "true");
  localStorage.setItem("user", JSON.stringify(response.data));

  setError("Access denied. You do not have administrative privileges.");
}

There is no separate admin route and no second admin key in this flow. The server decides whether the account is an admin; the frontend only records that decision. A non-admin receives a clear error even though the credentials were valid.

15.7 Firebase placeholder

frontend/src/firebase/firebase.js initialises Firebase Auth and a GoogleAuthProvider, but the config uses placeholders such as YOUR_API_KEY and YOUR_PROJECT_ID. No page imports the provider, so Google sign-in is not wired into the UI. It is safe to describe this as prepared scaffolding rather than a working feature.

15.8 Auth state problems

  • JWT is stored in localStorage, readable by any JavaScript on the page. A successful XSS can steal it. HttpOnly cookies are safer for production.
  • isAdmin in localStorage is user-controlled. It must never be trusted by the API.
  • No token expiry check or refresh. Expired tokens produce 401s until the user manually logs out.
  • The three auth paths store different keys: signup stores token + user, normal login stores only token, admin login stores all three. Pages must therefore tolerate a missing user object.
  • The navbar state and page state are not synchronised through context.
  • The “Remember me” checkbox is cosmetic; sessions persist until logout either way.
  • Logout is a full page reload, which clears transient state but is heavier than client navigation.

15.9 What happens on refresh

The token remains in localStorage, so every route guard still treats the user as logged in. React state resets, so pages refetch their data. After a normal login there is no stored user JSON, which is why the navbar and profile must rely on the token and the profile endpoint rather than cached user details.

Viva connection

“Signup and login return a JWT signed with JWT_SECRET. The frontend stores it and sends it as a Bearer token. The backend protect middleware verifies the signature and loads the current user, so role checks reflect the database rather than the localStorage flag.”

Note Viewer and Markdown Parser

Notes are stored as extracted text, not as rendered HTML. A heuristic parser turns that text into headings, paragraphs and lists, then the viewer adds a table of contents, scroll progress and reading time.

17.1 Loading a note

const res = await axios.get(`/api/notes/${id}`);
setNote(res.data);

The viewer reads the note id from the route /notes/:id. If the note is missing or the request fails, it shows an error panel rather than a blank page.

17.2 Heading extraction

const headings = useMemo(
  () => (note ? extractHeadings(note.content || "") : []),
  [note]
);

extractHeadings runs the same detection used by the renderer. That matters because the generated heading ids must line up with the table of contents. If the parser emitted a heading only during rendering, the TOC could point to the wrong element.

17.3 What counts as a heading?

RuleExampleLevel
Unit/module/chapter/topic/lesson/lecture/part/section + numberUnit 1: Introduction2
Numbered title with one number1. Data Types2 if major, otherwise 3
All-uppercase line with at least four lettersOPERATORS3
PDF TOC unit titleProgramming Fundamentals2

Lines longer than 90 characters, page-number lines, metadata lines and bullet lines are rejected. “Sem” lines are explicitly excluded to avoid semester headers becoming chapters.

17.4 PDF TOC reconstruction

parsePdfToc scans the first 100 lines for a bulleted unit list. It can reconstruct a hierarchy when the document has:

Unit 1
• Topic A
• Topic B
Unit 2
• Topic C
• Topic D

The parser requires at least three units and two children per unit before trusting the TOC. It then fuzzy-matches later labels to unit and section titles, using lowercase alphanumerics and a two-character prefix tolerance.

17.5 Rendering

const html = renderPlainText(note.content);
<div dangerouslySetInnerHTML={{ __html: html }} />

dangerouslySetInnerHTML is safe here because every piece of note text is escaped with escapeHtml before tags are added. The function builds only p, h2, h3, ul, li and label markup. It does not accept raw HTML from the note.

Security point

If a future change interpolates note text without escaping, this becomes an XSS sink. Keep the escape-before-tag rule explicit in code review.

17.6 Paragraph and list handling

if (isBulletLine(line)) {
  flush();
  if (!list) list = [];
  list.push([stripBulletMarker(line)]);
}
if (list) {
  if (looksLikeNewBlock(line)) { flushList(); para.push(line); }
  else list[list.length - 1].push(line);
}

Bullet markers include common Unicode bullets, the private-use range used by PDF extractors, and the replacement character. Consecutive lines after a bullet become part of the same list item unless they look like a new block.

17.7 Table of contents and scrolling

headingEls.current = headings.map((_, i) => document.getElementById(`nv-sec-${i}`));

The TOC lists headings with indentation by level. Clicking an entry calls scrollIntoView({ behavior: "smooth" }). A scroll listener computes:

progress = window.scrollY / (scrollHeight - clientHeight) × 100

and highlights the nearest heading above the viewport. The listener is registered as passive and removed on unmount.

17.8 Reading time

const readingTime = Math.max(1, Math.round(wordCount / 200));

At 200 words per minute, a 600-word note shows about 3 minutes. The minimum is one minute. This is a display estimate, not tracked analytics.

17.9 Marking as read

if (token) {
  await axios.post(`/api/certificate/notes/${note._id}/read`, {}, {
    headers: { Authorization: `Bearer ${token}` },
  });
}

The read marker is sent when the note opens, not when the student reaches the bottom. A student can therefore mark a note complete immediately. If you wanted genuine completion, track scroll depth and send the read event only near the end.

17.10 Code detection

The viewer labels a note as JavaScript when the content looks like code:

/\bconst\s+\w+\s*=|useState|\bfunction\s+\w+\s*\(|\blet\s+\w+\s*=\s*["'{([]/

This controls an icon/badge only; it does not syntax-highlight. The note is still rendered as text.

17.11 PDF download

<a href={`/api/notes/${note._id}/pdf`} target="_blank" rel="noreferrer">Download PDF</a>

The download endpoint streams the GridFS file with a filename and application/pdf content type. Opening the PDF does not mark the note as read; only the viewer mount does.

17.12 Parser limitations

  • Heuristics can misclassify short title-case lines as headings.
  • Tables and images from the original PDF are flattened to text and lost.
  • Two-column PDFs may interleave lines.
  • The TOC parser only looks at the first 100 lines.
  • No true Markdown syntax is supported; it is plain-text reconstruction.
  • Very long notes render in one pass with no virtualisation.
Viva answer

“We extract text from PDFs with pdf-parse, store it in MongoDB, and rebuild readable structure with a heuristic parser. We escape all text before generating HTML, which keeps dangerouslySetInnerHTML safe. It is a presentation layer, not a full PDF renderer.”

18.5 Score parsing

const parts = scoreStr.split("/").map(s => parseInt(s.trim()));
return { obtained: parts[0] || 0, total: parts[1] || 100 };

If the score string is malformed, the total defaults to 100. This hides bad data but can distort charts. It also means a missing score is treated as zero out of 100.

18.6 Accuracy

accuracy = round(Σ obtained / Σ maximum × 100)

This is a weighted average, not the mean of per-test percentages. A 40-question test therefore contributes more than a 10-question test. The result is a percentage of total marks earned, which is the more meaningful aggregate.

activities.slice(-10).map(...percentage...)

The last ten activities are plotted as percentages, labelled Test 1–10. The chart also compares the last two values and prints an “Improving” or “Declining” message. Because activity is appended in submission order, the trend is chronological if the array is stored oldest-first.

18.8 Subject grouping

if (title.includes("bca")) subject = "BCA";
else if (title.includes("bba")) subject = "BBA";
else if (title.includes("biotech")) subject = "Biotech";
else subject = "General";

This groups by text in the activity title, not by a stored course or subject id. A title that does not contain one of those words falls into “General”. A schema-level course and subject on the activity record would be more robust.

18.9 Monthly activity and streak

monthKey = `${year}-${String(month + 1).padStart(2, "0")}`

The monthly chart keeps the last six month buckets. The streak counts consecutive distinct activity dates, starting from today or yesterday. Multiple tests on one day count once. If the most recent activity is older than yesterday, the streak is zero.

Stats that are not recalculated

The dashboard displays performanceStats.rank, hoursLearnt and avgScore, but the codebase does not recompute them on test submission. Unless they are seeded or updated elsewhere, they remain defaults or stale. The reliable figures are the ones derived from recentActivity.

18.10 Analytics UI

The page has four tabs:

  • Overview — summary cards and recent trend.
  • Progress — score progression over the last ten tests.
  • Subjects — per-subject accuracy circles.
  • History — full activity table with score percentages.

21.12 Data integrity gaps

  • No cascade delete: deleting a note does not remove its id from users’ readNotes.
  • No cascade delete: deleting a test leaves results and purchases pointing at a missing test.
  • Activity is unbounded and duplicates summary data.
  • Results are denormalised snapshots by design; later test edits do not rewrite old results.
  • Certificates are snapshots by design; later profile edits do not rewrite them.

These are the sequences to trace in a viva. Each flow lists the exact actors, requests, state changes and failure points.

23.1 Registration and login

Browser → POST /api/auth/signup
        → validate names, phone, domain
        → check duplicate email
        → bcrypt hash password (10 rounds)
        → User.create
        → sign JWT { id }
        → 201 { token, user fields }
Browser → save token (+ partial user) → redirect /
Later   → GET /api/auth/profile with Bearer token
        → protect verifies JWT → loads user → returns profile

Failure points: duplicate email, unsupported domain, MongoDB offline, weak client password, JWT secret missing. The backend does not currently call isStrongPassword during registration, so a direct API call can create a weak password.

23.2 Password reset

POST /auth/forgot-password { email }
→ find user (or return generic success)
→ generate 6-digit OTP
→ hash OTP with SHA-256, set expiry 10 min, attempts 0
→ send email (or log OTP when SMTP missing)
→ generic 200 response

POST /auth/verify-reset-otp { email, otp }
→ compare SHA-256 hash, check expiry and attempts
→ increment attempts on failure
→ issue short-lived reset JWT with purpose + jti
→ store hash of jti/hash token on user

POST /auth/reset-password { resetToken, password }
→ verify signature, purpose, jti hash
→ enforce strong password
→ bcrypt hash and save
→ clear OTP/reset fields
→ 200 “You can now sign in”

The generic forgot-password response prevents account enumeration. The OTP is never stored in plaintext. The reset token is single-use because its hash is cleared after success.

CHAPTER 24

Security and Code Quality Audit

The application has a sound core—bcrypt password hashing, signed JWTs, server-side scoring, ownership checks on results and certificates, and escaped note rendering. The main weaknesses are inconsistent admin authorization, an unverified manual payment path, and missing operational hardening.

24.2 Authentication and authorization

What is correct

  • Passwords are hashed with bcrypt, cost 10, and the hash is select:false.
  • JWTs are signed with JWT_SECRET and expire after seven days.
  • Login returns the same “Invalid email or password” message for both wrong email and wrong password.
  • Password reset stores an OTP hash, not the OTP, with a 10-minute expiry, 60-second resend cooldown and five-attempt limit.
  • Reset tokens are purpose-scoped, single-use and stored as hashes.
  • Results and certificates are queried with the current user id.

What to fix

  • Call isStrongPassword in registration. It currently exists but is unused there.
  • Add a reusable adminOnly middleware and apply it to every admin route.
  • Do not trust isAdmin from localStorage; the backend role check is the only authority.
  • Consider short-lived access tokens plus refresh tokens, or HttpOnly secure cookies.
  • Add a token version or denylist if immediate logout/revocation is required.
  • Normalize emails to lowercase before storing and querying to avoid case-variant duplicates.

24.4 Payment security

// current access rule
const purchase = await Purchase.findOne({ userId, testId });
return Boolean(purchase);

This ignores status. Tighten it:

const purchase = await Purchase.findOne({
  userId,
  testId,
  status: { $in: ["paid", "manual", "simulated"] },
});
  • Manual UTR is self-reported. Require admin approval or a real provider webhook.
  • After signature verification, fetch the Razorpay payment and compare amount, currency and status.
  • Store the provider order amount and verify it equals the current test price.
  • Do not expose a "simulate" path in production builds.

24.5 Input, uploads and files

  • Multer uses memory storage for notes/PYQ with no file size limit. A large upload can exhaust RAM.
  • There is no MIME or extension allow-list. Validate PDF magic bytes and cap at a sensible size (for example 20–50 MB).
  • The QR upload accepts any extension and replaces the old file by path; validate image types and size.
  • PDF parsing runs in-process. A malicious or malformed PDF could crash the worker; isolate parsing in a child process or queue.
  • Mock-test PDFs remain in uploads with server-generated names but are not cleaned up when a test is deleted.

24.6 Data exposure

  • /api/admin/students returns names, emails and student ids without a token.
  • /api/admin/stats returns aggregate enrollment trends publicly.
  • AI error responses include upstream details, which may reveal provider internals.
  • The admin login stores the whole login response in localStorage, including isAdmin and token.
  • No secret values are committed in the frontend; the Groq, Razorpay secret, Mongo URI and SMTP credentials stay server-side.

24.7 XSS and rendering

renderPlainText calls escapeHtml on every text fragment before inserting tags. The only way to inject markup would be to change that code to concatenate unescaped note content. The note body is therefore not an XSS sink today.

escapeHtml(str)
  .replace(/&/g, "&amp;")
  .replace(/</g, "&lt;")
  .replace(/>/g, "&gt;")
  .replace(/"/g, "&quot;")
  .replace(/'/g, "&#39;");

The code-preview iframe uses sandbox="allow-scripts" without allow-same-origin, so user HTML cannot access the parent origin. This is the correct choice.

24.9 Code quality observations

  • AdminDashboard.jsx exceeds 1,000 lines; split by section.
  • Auth headers are duplicated in every page; centralise an Axios instance with interceptors.

24.10 Prioritised remediation plan

  1. Lock down the four public/PII admin endpoints and note/PYQ mutations with an admin guard.
  2. Disable or gate the manual UTR flow; require verified payment.
  3. Enforce strong passwords on the server and add auth/OTP rate limits.
  4. Add upload size and type validation; clean up orphaned files.
  5. Require a purchase status in hasAccess; re-verify Razorpay amount.
  6. Add Helmet, restricted CORS, structured logging and health checks.
  7. Move tokens to HttpOnly cookies or add refresh/revocation.
  8. Refactor the admin dashboard and shared API client.

CHAPTER 27

Rapid-Fire “Why” Answers

Short, defensible answers to the questions examiners actually ask. Each answer names a trade-off rather than pretending the design is perfect.

Why did you choose the MERN stack?

One language across the stack, JSON end to end, and fast iteration. MongoDB suits document-shaped content like tests with embedded questions, and React fits a highly interactive exam UI.

Why MongoDB instead of MySQL?

The test document naturally contains an array of questions and options, so embedding avoids a join-heavy schema. The trade-off is weaker relational constraints, which is why some integrity checks live in application code.

Why JWT instead of sessions?

Stateless authentication works well for an SPA and a separate API; the server does not need a session store. The trade-off is revocation: a stolen token remains valid until expiry.

Why store the JWT in localStorage?

It is simple and works with the Vite proxy and Bearer headers. It is also readable by JavaScript, so an XSS would steal it. HttpOnly cookies are the safer production choice.

Why bcrypt?

It is intentionally slow and salted, making offline brute force expensive. Ten rounds balance security and login latency.

Why hide the password field?

select:false keeps the hash out of normal queries. Login explicitly requests +password only when it needs to compare.

Why server-side scoring?

The browser is untrusted. The server owns the correct answers, computes +4/−1, and stores the result. The client cannot inflate a score.

Why +4 and −1?

It mirrors common competitive-exam marking: reward correct knowledge and penalise guessing, while leaving unattempted questions neutral.

Why hide correct answers in the list and test payload?

A student could inspect network responses. Projecting out questions.correctAnswer prevents casual cheating; the review endpoint reveals them only after submission and only to the owner.

Why a separate Purchase collection?

Access is a many-to-many relationship between users and tests. A join collection with a unique pair supports free, paid, manual and simulated states cleanly.

Why the unique compound index on Purchase?

It makes access idempotent: repeated orders or verification cannot create duplicate rows. Upsert relies on it.

Why does hasAccess ignore status?

It is a simplification, not a good final design. It should require a paid/manual/simulated status so a pending row cannot unlock content.

Why is there a manual UPI path?

It lets the project demonstrate checkout when Razorpay keys are unavailable. It is explicitly labelled simulated and is not real payment verification.

Why is Razorpay amount multiplied by 100?

Razorpay’s API expects the smallest currency unit, paise. ₹99 becomes 9900.

Why verify the Razorpay signature?

The HMAC proves the order/payment pair was signed with the server’s secret. Without it, a client could claim a fake payment.

Why use GridFS for PDFs?

PDFs can exceed the 16 MB document limit and should stream. GridFS chunks them and stores metadata; the document keeps only the file id.

Why extract text from PDFs?

It enables a responsive web reader, searchable headings and reading progress. The PDF remains available for download.

Why is the markdown parser heuristic?

Text extraction loses font and layout information. The parser infers headings from numbering, uppercase lines and PDF table-of-contents patterns. It is best-effort, not a full document model.

Why escape note text before using dangerouslySetInnerHTML?

The parser generates HTML, so React’s normal escaping is bypassed. Escaping every text fragment before adding tags prevents stored XSS.

Why store a certificate snapshot?

A certificate is a historical record. If a student later changes college or name, the issued certificate should not silently change.

Why isn’t a score required for a certificate?

The product defines completion as consuming all material and attempting all tests. A score threshold would be a policy change, not a technical one.

Why normalise course aliases?

URLs and content use variants like bio, biotech and biotechnology. Normalisation keeps progress and certificate lookup consistent.

Why is the same test allowed multiple times?

Students benefit from retakes, and the Result collection preserves each attempt. Analytics treats each attempt as activity; a unique result index would remove that ability.

Why is activity stored on the user?

It keeps the profile and analytics fast with one document read. The cost is an unbounded array and duplicated summary data; a separate Activity collection would scale better.

Why don’t rank and hours update?

The UI expects them, but the backend only increments testsTaken. They are placeholders. A real implementation would aggregate results or maintain a scheduled leaderboard.

Why React?

The exam screen has many interdependent pieces of state—answers, palette, timer, results. Component state and declarative rendering make that manageable.

Why Vite?

Fast dev startup, hot module replacement and a simple proxy for /api and /uploads.

Why React Router?

It gives clean URLs, nested layouts, route params and client-side navigation without full reloads.

Why are ProtectedRoute and AdminRoute not security?

They run in the browser and read editable localStorage. They improve navigation; the server middleware and role checks are the actual boundary.

Why does the admin dashboard still work with public APIs?

Because some admin read routes lack guards. The UI sends a token for many calls, but the server does not require one for stats, students or course creation.

Why use a Vite proxy?

It makes /api same-origin during development, avoiding CORS and keeping URLs identical to production.

Why does the chatbot hardcode localhost?

It was written independently of the shared API pattern. It is a deployment bug, not a design choice; replace it with a relative URL.

Why proxy AI and TTS through the backend?

The Groq key must stay server-side, and Google TTS blocks direct browser calls. The backend also normalises responses.

Why is the AI endpoint unauthenticated?

It was built as an open helper. That exposes quota and enables abuse; it should be authenticated and rate-limited.

Why sandbox the code preview?

User HTML can contain scripts. Omitting allow-same-origin isolates it from the app’s storage and DOM.

Why send code to Wandbox?

Running arbitrary languages securely requires containers or VMs. Wandbox provides that externally; the trade-off is privacy, latency and availability.

Why is the timeout submit potentially wrong?

The timer effect captures an old handleSubmit closure. Without a ref or updated dependency, it can submit stale answers. This is a React stale-closure bug.

Why show a zero result when submit fails?

It is a bug, not intended behaviour. The catch block fabricates zeros instead of surfacing an error and allowing retry.

Why no database transactions?

The flows are mostly single-document and the project prioritised simplicity. Multi-step operations like result + activity + certificate are therefore not atomic.

Why is there no automated test suite?

The project is a prototype and verification was manual. The highest-value tests would cover auth, payment verification, scoring and certificate completion.

What would you fix first?

Authorization consistency: protect the public admin endpoints and note/PYQ mutations, then remove or gate the unverified UTR flow.

What is the strongest part of the project?

The end-to-end learning loop: content ingestion, server-scored assessment, analytics and automatic certificate issuance, all tied to one account.

What is the weakest part?

Security hardening around admin operations and payments, plus the lack of automated tests.

How would you scale it?

Move files to object storage, add Redis for sessions/rate limits, queue PDF parsing, split the admin SPA, add indexes for results, and introduce a proper payment webhook.

Why keep the PDF after extracting text?

Students may want the original layout, and extraction can be imperfect. The PDF is the source of truth; the text is a reading convenience.

Why does the certificate route create the certificate on a GET?

It makes issuance automatic when the student checks progress. A stricter REST design would use a POST or a background job, but the side effect is idempotent because an existing certificate is reused.

Why is the app name inconsistent?

The UI says “Mentor Lab”, the frontend package is drona-gyan, and some footers say “Drona Gyan”. It reflects the project’s evolution. The backend package is monitor-lab-backend.

28.10 Final summary

Mentor Lab is a full-stack learning platform built around a complete student loop: discover a course, read structured notes, attempt server-scored mock tests, review mistakes, track progress, and earn a completion certificate. It combines a React SPA with an Express/MongoDB API, GridFS file storage, JWT authentication, Razorpay integration with a demo fallback, and AI/TTS study helpers.

The engineering strengths are clear separation of frontend and backend, server-side assessment integrity, ownership checks on personal records, and pragmatic use of embedded documents for quiz content. The engineering risks are equally clear: inconsistent admin authorization, unverified manual payments, and missing operational hardening. A good viva answer should present both—what works, why it was chosen, and exactly what you would change next.
